# Open Agent Mesh 项目章程（长期有效）

**项目目标：** 构建一个与模型厂商及 Agent 框架无关的 Agent-to-Agent 开放协作基础设施，让获得授权的 Agent 能够发现彼此、委派任务、共享必要上下文、协商依赖并交付可审计的结果。

## 为什么做

当前 Agent 生态碎片化：不同工具、用户和模型之间缺少统一协作接口；长任务上下文难以延续；任务并发冲突、权限边界、信任与成本缺乏标准的基础设施。本项目通过 A2A / HTTP / Agent Skills 等开放接口提供统一协作层；MCP 负责面向工具的连接能力。

## 产品定位

- **Open Core：** 开放协议网关、开发 SDK、基础协调器和本地运行能力
- **可选商业能力：** 托管协作网络、企业租户权限、审批、审计、治理、观测、配额和计费
- **部署：** 本地优先，未来支持私有云、公有云与混合部署
- **兼容：** Python/Node 及主流 Agent 框架；托管 ChatGPT、Cursor 等只能通过其实际开放的 API、Skill、插件或工具接口接入

## 研发原则

1. GitHub 仓库为技术事实来源；需求、实现、测试、技术决策与变更记录都要纳入版本管理。
2. 每次可复现的改进应附测试、记录及兼容性说明。未经测试不宣称已上线。
3. 严格区分原型、Beta、生产能力和商业验证结论。
4. 不上传 Token、凭证、客户资料或第三方专有代码。
5. 遵循 A2A / MCP 标准，但不声称获得未经验证的官方认证。
6. 区分 agent-to-agent 信任边界与 agent-to-tool 权限，拒绝越权调用和隐式凭证共享。
7. 重要操作需审批、权限隔离、幂等、防环路和可审计记录。
8. 优先完成可运行的端到端用例，而非扩张宣传口径。

## 长期维护规则

- 功能提交：源码 + 测试 + 必要文档同步更新。
- 研究提交：在 docs/ 下形成有日期、有证据、有结论、有待验证假设的记录。
- 架构决策：记录背景、备选方案、权衡及最终决策。
- 任务跟踪：GitHub Issues / Pull Requests 与里程碑。
- 版本发布：语义化版本、CHANGELOG 与兼容性说明。
- 安全变更：优先通过 PR 审核并附影响分析。

**同步边界：** 只有在本项目的开发/研究任务被实际执行时，才能同步提交；没有运行中的代理或自动化时，本聊天本身不能无人值守监控所有未来变化。持续 CI 能自动检查推送的代码，不代表会自动研发或推送新发现。

## 初期重点

协议一致性测试、SSE 与任务续接、可靠队列和分布式租约、MCP 桥接、多租户与审批、共享记忆的证据与版本治理、事件追踪与成本计量。
